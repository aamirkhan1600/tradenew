## 1 · Critical — synthetic instruments were tradable

**Found:** the instrument table contained 7 rows from the integration script,
carrying both brokers' tokens for strikes that do not exist:

```
BANKNIFTY 38350 CE | z: 9003 BNF38350CE | k: K9003 BANKNIFTY38350CE | tradable: 1
```

They were the **only** rows marked tradable. With Kotak connected and a strategy
enabled, the scanner would have selected one and sent `K9003` to the broker as a
real order.

**Cause:** the e2e script seeded contracts and deleted only its user-scoped rows
on teardown. It also used a *real* upcoming expiry, so it could have overwritten
genuine contracts' tokens with fakes.

**Fixed** at three levels:
* the rows were deleted;
* the script now cleans up its instruments and uses expiry `2099-12-31`, which
  can never collide with a real contract, and refuses to run under
  `NODE_ENV=production`;
* **structurally** — a successful sync now prunes option rows that neither
  master listed (`repo.instruments.pruneStale`), which also removes expired
  series. Guarded so a truncated download cannot empty the universe, and using
  the *database's* clock because `synced_at` is set server-side.

## 2 · High — the square-off button could do nothing

**Found:** the web tier wrote the request into `strategies.state`; the engine
rewrites that same column **every tick**. A request had well under a second to
be read before being overwritten.

This is the operator's emergency control, and its failure mode was silent —
the UI reported success.

**Fixed:** dedicated `square_off_requested_at` / `square_off_requested_by`
columns. The web tier sets them; the engine claims them with a conditional
`UPDATE`, so two engines cannot both act on one request. The request is now
audited on both sides.

---

## 3 · High — `reentryAfterStop: false` stopped working after a restart

**Found:** `nextEntryAllowedAt` returned `Infinity` for "no more entries today".
The runtime is persisted as JSON, and `JSON.stringify(Infinity)` is `null` —
which reads back as falsy and re-enables entry.

Verified live:

```
in memory        : blocked
after a restart  : NOT blocked   ← re-entry silently re-enabled
```

`reentryAfterStop: false` is a **shipped default**, so a strategy that took a
stop and was restarted would trade again the same day against the operator's
instruction.

**Fixed:** the block is now an end-of-IST-day timestamp — a real instant that
survives serialisation. Three regression tests cover the round trip, the
boundary and the ordinary cooldown.

## 4 · High — an unknown exit outcome was retried

**Found:** in `exitPosition`, an uncertain buy-back hit

```js
this.state = buyBack.uncertain ? S.POSITION_OPEN : S.POSITION_OPEN;
```

Both branches identical. An exit whose outcome we never learned went back to
monitoring and re-attempted the exit every time the price met the target.

The idempotency key prevented a genuine double order, so this degraded into a
loop rather than a duplicate trade — but the position's true state was unknown
and no human was told.

**Fixed:** an uncertain buy-back sets the trade `NEEDS_ATTENTION`, logs at error
level and moves the strategy to `HALTED`. Retrying could leave a naked long if
the order did fill; not retrying leaves a short if it did not — neither is safe
to automate. A clean rejection still returns to `POSITION_OPEN` and retries,
which *is* safe.

## 5 · Medium — index rows duplicated on every sync

**Found:** 47 index rows where there should be 6.

```
BANKNIFTY  12 rows | token 260105
NIFTY       7 rows | token 256265
...
```

**Cause:** index rows were stored with `NULL` expiry and strike. **MySQL treats
NULLs as distinct in a UNIQUE index**, so `ON DUPLICATE KEY UPDATE` never
matched and every sync inserted a fresh row.

**Fixed:** index rows now carry sentinels (`expiry_date = '1970-01-01'`,
`strike = 0`) that are unreachable as real contract values, so the key matches
and the upsert updates. The migration collapsed the existing 47 rows to 6.

---

## 6 · Medium — a crash could orphan a live position

**Found:** the hedge is placed, then the trade row is written. A failure between
the two left a live hedge at the broker with no trade record; reconciliation
found no open trade and went quietly `IDLE`, after which the strategy would open
a *second* position while the first sat unmanaged.

**Fixed:** `repo.orders.placedWithoutTrade()` looks for orders confirmed at the
broker with no `trade_id`. Reconciliation now halts and escalates instead of
resetting.

---

## 7 · Medium — the WebSocket 403 loop

**Found** in the operator's own logs: a 403 handshake retried every 30 seconds
indefinitely, with no error ever raised.

Two independent causes:
* only the REST poller checked `err.isAuth`; the WebSocket path had no auth
  handling at all;
* the REST poller returns early when nothing is subscribed — which is the case
  before any strategy runs — so the dead session was never detected.

A third would have appeared once a strategy ran: the engine calls `feed.attach`
every tick, so a ticker deleted on auth failure was rebuilt **once a second**.

**Fixed:** a 401/403 handshake latches `authFailed`, reports once at error level
and stops; `feed.attach` refuses to rebuild a ticker for an `EXPIRED`/`ERROR`
session; a fresh token clears the latch so re-login works. Verified:
`authFailed: true | reconnects attempted: 0 | auth_expired events: 1`.

## 8 · Low — session windows were unbounded

A strategy could be configured with `entryTime: 08:00` (no quotes exist, so it
would sit in `SCANNING` all morning with no explanation) or
`squareOffTime: 16:30` — **after the close, meaning the time exit would never
fire**. Now validated against 09:15–15:30 IST.

## 9 · Low — dynamic SQL in `trades.patch`

The one place the app built SQL from object keys. Every caller was internal, but
the allow-list costs nothing and removes the possibility that a future caller
passes something user-derived. Ownership columns are explicitly not patchable.

## 10 · Low — a session repaired outside the app stayed dark

Defect 7's fix is correct but has a consequence: a session marked `EXPIRED` or
`ERROR` is never rebuilt automatically, because retrying a rejected token is
pointless. Yet the repair for the most likely cause — a missing entitlement —
happens in the *broker's* console, where this application cannot see it. The
feed would have stayed dark until someone remembered to press a button.

**Fixed:** the engine re-probes failed sessions every five minutes
(`feed.recoverFailedSessions`) and restores any that now work. Only sessions
that still hold a token are probed; a `DISCONNECTED` account has none, and only
a fresh login can help it. Verified against the live account: the probe runs,
correctly declines to recover while the entitlement is still missing, and leaves
the status at `ERROR`.

## Environment findings — not code defects

**Zerodha market data is not entitled on the app.** Each scope probed
separately, which is what makes the diagnosis exact rather than a guess:

| Scope | Endpoints | Result |
| --- | --- | --- |
| Session | `/user/profile` | success — LTB651 |
| API access | `/user/margins`, `/orders`, `/portfolio/positions` | success |
| **Market data** | `/quote/ltp`, `/quote/ohlc` | `PermissionException` |

The token is valid and the app has API access; **market data alone is missing**,
and that single entitlement also governs the WebSocket — hence the 403. Until it
is enabled **no strategy can trade**, because the engine correctly refuses to
open a position without a healthy feed. Enable it at `developers.kite.trade`.

Because that fix happens outside this application, the engine now re-probes
failed sessions every five minutes (defect 10) and restores them automatically.

**Kotak is not connected**, so `tradable` is legitimately 0 — no contract is
orderable until the Kotak master has been synced against a live session.

## Residual risks

Stated plainly; none are defects, all are limits.

1. **No live-API verification.** The Kotak order path has never placed a real
   order and the ticker has never received a real tick. Both are written to the
   documented contracts and unit-tested against synthetic frames. **Run paper
   first.**
2. **Reconciliation is heuristic.** Kotak has no client order reference, so an
   `UNKNOWN` order is matched on `(token, side, qty)`. Ambiguity escalates to a
   human rather than guessing, which is the right failure mode but still means
   manual work.
3. **No partial-fill handling.** Orders are market orders on liquid index
   options, treated as all-or-nothing. A partial fill would be visible in
   `orders.filled_qty` but is not acted on.
4. **`liveStatus` issues one query per strategy per poll.** Fine at this scale,
   would need a join at hundreds of strategies.
5. **The candidate is up to one tick (~1 s) old** when the hedge is placed. The
   order is a market order, so the exposure is to slippage rather than to a
   wrong selection.
